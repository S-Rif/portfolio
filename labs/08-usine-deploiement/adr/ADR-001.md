# ADR-001 · Planifier les scripts : timer systemd ou CronJob Kubernetes

- **Statut** : proposé
- **Lab** : 08 · Usine de déploiement on-prem

## Contexte

Les scripts de maintenance tournent sur des serveurs fournis par l'usine, sans cluster Kubernetes. Il faut les planifier, les superviser, les relancer et revenir à une version précédente, à 0 € et sans ajouter de plateforme à exploiter.

## Options

| Option | Coût | Avantages | Limites |
| --- | --- | --- | --- |
| Timer systemd | 0 € | Natif sur les serveurs, journal (`journalctl`), rattrapage (`Persistent=true`), dépendances, déployé par Ansible | Planification par serveur, pas d'orchestration entre machines |
| `cron` | 0 € | Universel, connu de tous | Aucun journal structuré, pas de dépendances, échecs silencieux |
| CronJob Kubernetes | Coût d'un cluster à exploiter | Planification déclarative, relance et historique intégrés | Exige un cluster absent du périmètre ; image par script |
| Ordonnanceur dédié (Rundeck, AWX) | 0 € en communautaire, exploitation lourde | Interface, droits, chaînage de tâches | Une plateforme de plus à maintenir pour ce besoin |

## Décision

Timers systemd, déployés par un rôle Ansible depuis le pipeline. Le besoin est une planification par serveur, observable et réversible ; c'est exactement ce que systemd fournit sans plateforme supplémentaire.

## Conséquences

- (+) 0 €, rien à exploiter en plus, état lisible par la supervision existante.
- (−) Aucune vue centrale des exécutions : à compléter par la remontée des statuts (bonus L08-O10) ou par la supervision.

## Déclencheur de revue

Le client dispose d'un cluster Kubernetes exploité, ou les scripts doivent s'enchaîner entre plusieurs serveurs.
